# 团队分工与交付顺序

把任务先按三条线拆。两个人时可由一人兼顾训练与分析，另一人负责验证与提交；认领时直接在团队任务单里填负责人。

| 负责线 | 现在做什么 | 交给下一位什么 |
|---|---|---|
| A · Harness 与训练 | 保存实跑 Harness、当前最佳候选和训练回执；排查失败反馈；对 `bp-ng45` 的退步按同种子拆 WNS/TNS，优先检查是否真的改变了分层 | 实跑版本、完整候选 ID、九组成绩、父版本与主要涨跌，标清最终选择状态 |
| B · 环境与验证 | 核对官方包版本、Docker 和 GPU；先做 `contest2 check`；等 A 给出正式选中的候选后跑两例六组 | 环境记录、训练与验证的 15 组公开产物、失败组对应的日志和原因 |
| C · 报告与提交 | 从第一天起整理技术报告和复现说明；汇总 Harness、算法与运行日志，核对提交清单后由队长上传 | 可复现的压缩包、报告、共享链接，版本与候选 ID 一致 |

1. **先保住已有结果。** 在任何新实验前，归档当前赢家的候选源码、训练矩阵和九组回执。保存新实验自己的预算账本，不混用工作目录。
2. **并行补证据。** A 看跨种子表现和失败日志，B 准备独立验证环境，C 把已有结果和待办写进报告。若试新版，在同起点、同预算下对照，记录模型提案被拒以及实际送评的次数。
3. **选定后锁版本。** 记下冻结候选 ID、Harness 提交号和官方包版本。用该候选补跑六组验证，验证结果留给报告。
4. **交付前核对。** 九组训练、六组验证、对应的切分和布局、日志、候选源码、Harness 与技术报告都要能相互对应。将原始私密运行信息留在团队自己的安全存储。

每轮交接发四项就够：`候选 ID / 9 组状态 / 完整分数 / 下一步和负责人`。未跑齐就写 `x/9`，不要用部分均分报成总成绩。
